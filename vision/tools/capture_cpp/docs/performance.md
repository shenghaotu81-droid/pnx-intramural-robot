# 实拍基线与 1.1.0 优化依据

## 1.0.0 实拍

样本为 `~/Downloads/maix-capture-cpp/video_19700101_001054_555828_633.{csv,h265}`。H.265 裸流可完整解码 550 帧，FFprobe 报告可见 1440×1080、编码宽 1472、标称 30 fps。CSV 帧号从 0 连续到 549。首尾有 549 个采样间隔，按单调时钟算出 **38.328876 s、14.32 fps**。

| 实测指标 | 软件采集时间 `t_us` | 硬件 `vpss_pts` |
| --- | ---: | ---: |
| 首尾跨度（本样本按微秒换算） | 38.328876 s | 38.330096 s |
| 间隔中位数 | 65.585 ms | 66.627 ms |
| P95（最近秩） | 99.992 ms | 99.985 ms |
| 最长间隔，335 → 336 | 1367.101 ms | 1366.694 ms |
| 次长间隔，0 → 1 | 262.915 ms | 263.405 ms |

若将硬件间隔除以 33.333 ms 后四舍五入，269 个间隔落入 1 周期桶，236 个落入 3 周期桶。前者实际为 **34.731–39.553 ms，中位数 38.075 ms**，只有 5 个间隔落在 33.333 ± 2 ms 内。三周期桶中位数为 95.265 ms。相邻间隔中，短桶接三周期桶出现 227 次，反向出现 221 次。下一轮需同时比较间隔分布和平均帧率。

第 335、336 帧的编码包均为普通帧，分别为 27,273 和 29,046 字节。两个时钟都记录到大间隔，文件只能证明送达应用的相邻帧时间相隔这么久。传感器出帧、VPSS 可用缓冲、VENC 等待和存储阻塞各占多少时间，旧文件缺少调用级证据。单凭 269 个短间隔也无法确认相机持续交付 30 fps 的能力。

## 此轮改动

1. 旧循环在拿到首帧后才建文件、初始化编码器。1.1.0 在预热时确认原生宽度，开始录像时先准备文件和编码器，再取首帧。首行的 `open_us` 可用于衡量启动代价。
2. 旧循环持有单缓冲相机帧，串行执行编码取流、写视频、写 CSV 和预览。1.1.0 在需要时读取本帧的预览或拍照像素，提交原生帧后立即归还。一个后台线程按提交顺序取流、写视频和两份时间文件。采集线程可以同时等待下一帧，上一笔输出未完成时会在下次提交前等待，等待量记入 `writer_wait_us`。这样既限制内存占用，也能观察存储变慢时的反压。原生帧的归还顺序参考了 SDK 自带录像器。 [MaixCDK 源码](https://github.com/sipeed/MaixCDK/blob/83f8b8d456813932526601a40757bdafe452e718/components/vision/port/maixcam/maix_video_mmf.cpp#L3578-L3590)
3. 屏幕按画面或按钮状态变化重绘。录像预览上限 8 Hz，相机仍请求 1440×1080 NV21、30 fps、单缓冲，VENC 仍为 H.265 CBR 6 Mbps、GOP 30。预览准备和实际屏幕渲染分别计时，可检查短长交替与预览是否相关。

1.1.0 的主机验证覆盖帧归还顺序、后台阻塞、停止收尾、解码和文件对齐。新版的板端平均帧率与最长间隔尚无实测结果。 [验证记录](validation.md) · [复测与日志字段](timing.md)
