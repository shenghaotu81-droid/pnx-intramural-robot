# 分段计时与长间隔定位

每段录像在 `/root/capture_cpp/` 生成三个同名文件。H.265 保存画面，三列 CSV 保存离线标定时间。性能日志使用 `.timing.tsv`，每个成功写入的编码帧对应一行，可按 `frame_index` 与 CSV 关联。在仓库根目录运行 `python3 vision/tools/capture_cpp/scripts/profile_capture.py <导出的录像CSV>`，即可核对两份时间文件，打印每段耗时的中位数、P95、最大值和五个最长采集间隔。P95 采用最近秩。

## 字段

所有 `_us` 字段均为微秒，来自同一单调时钟。时间点以首个成功录像帧的相机 pop 返回时刻为零。以下耗时测量调用前后的墙钟差，包括线程被抢占的时间。1.0.0 只有标定 CSV，1.1.0 和 1.2.0 的旧、新日志均可由统计脚本读取。可选步骤未执行时记 0。

| 字段 | 含义 |
| --- | --- |
| `frame_index`, `t_us` | 帧号和成功获取相机帧的时间点，与标定 CSV 相同。 |
| `pop_start_us`, `pop_us` | 成功取帧的起点和耗时，首帧起点可为负数。1.1.0 包含 VPSS 取帧、内存映射和缓存失效。1.2.0 单独计时 `CVI_VPSS_GetChnFrame`，在成功返回后、映射之前采样 `t_us`。 |
| `pop_timeouts`, `retry_us` | 此次成功取帧前连续返回空值的次数及其调用总耗时。连续五次失败会终止采集，最后一组失败写到应用控制台。 |
| `open_us` | 创建录像文件、初始化编码器和启动输出线程的总耗时，仅记录在第一行，发生于首次录像 pop 之前。 |
| `preview_us`, `photo_us` | 采集线程准备并发布预览，以及拍照时复制像素、派发 JPG 任务的耗时。1.2.0 把小图转色、放大移入 UI 线程的 `display_us`。 |
| `writer_wait_us` | 本帧送编码前等待上一帧输出的时间。1.1.0 等到写文件完成，1.2.0 等到压缩包入队。 |
| `push_start_us`, `push_us` | 本帧 VENC push 的起点与耗时。 |
| `release_us`, `hold_us` | push 后解除映射、归还原生帧的耗时，以及从成功取帧到完成归还的总耗时。后者包含预览、拍照、等待、push 和归还。 |
| `display_count`, `display_us` | 两次采样之间 UI 线程完成的重绘次数和重绘总耗时，包括画按钮和 `Display::show`。按完成时刻归入随后采样的日志行，屏幕上显示的图像可能来自更早的帧。 |
| `enc_pop_start_us`, `enc_pop_us` | 输出线程开始取当前编码包的时间点和 `Encoder::pop` 耗时。 |
| `packet_us`, `crop_us` | 检查、拼接压缩片段和释放 SDK 流的耗时，以及需要裁剪时修改 SPS 的耗时。 |
| `video_write_us`, `csv_write_us` | 分别调用缓冲文件流写视频和标定 CSV 行的耗时，包含写入引发的阻塞。实际介质回写受系统缓存影响，最后一次关闭文件发生在停止录像后。 |
| `output_end_us` | 标定行写完的时间点。随后输出线程缓冲写入本帧 TSV 行。最后一帧在停止录像时排空。 |

### 1.2.0 新增字段

| 字段 | 含义 |
| --- | --- |
| `cpu_mapped`, `pixel_map_us` | 本帧是否让 CPU 访问像素及映射耗时，含 libsys 内置的缓存失效。纯录像帧两项均为 0。映射在 `hold_us` 内。 |
| `vpss_time_ref`, `camera_buffers` | VPSS 描述符原始 `u32TimeRef` 和本次请求的相机缓冲数。TimeRef 的递增规则依驱动而定，可与 PTS 对照观察。 |
| `queue_wait_us`, `queue_depth` | 取流线程从复制完压缩包至取得写队列位置的等待时间，以及放入该包后排队的包数（1–8）。正在写的包另计。 |

## 读一个长间隔

设间隔为 A → B，CSV 中的 `Δt = B.t_us − A.t_us`。用 TSV 将其拆成两段，微秒取整可能引入 1 µs 差异。

1. **上次取帧后，过了多久才进入下次成功的 pop**。计算 `B.pop_start_us − A.t_us`。若偏大，查看 A 的 `hold_us`、预览、拍照、编码提交和等待，再看 B 是否有取帧重试。
2. **这次 pop 本身等了多久**。查看 `B.pop_us`。若上一步很短而此项很长，延迟落在 Camera 调用内部。1.2.0 可进一步区分 VPSS 调用与 `pixel_map_us`。传感器出帧和驱动内部排队仍需结合原始 PTS 分析。
3. **后台是否拖住了采集**。若 A 的 `writer_wait_us` 很大，向前检查 A−1 的 `enc_pop_us`、`video_write_us`、`csv_write_us` 和 `output_end_us`。1.2.0 的写盘耗时只在队列积满后间接阻塞提交，应检查先前若干帧的 `queue_depth`、`queue_wait_us` 和写入耗时。后台工作可与下一次取帧重叠，UI 也在另一线程。直接把三条线程的耗时相加会重复计算重叠部分。

采集线程和输出线程的可选步骤按实际执行情况解读。例如，录制中只有少数帧参与预览，汇总表会同时给出非零帧数。比较两次录像时，应使用相同的分辨率、存储介质和场景，并分别记录有无拍照的时段。
